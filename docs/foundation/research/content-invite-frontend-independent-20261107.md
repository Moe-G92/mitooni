## Primary provider evidence (accessed 2026-11-07)

- [Implicit flow](https://supabase.com/docs/guides/auth/sessions/implicit-flow): access/refresh tokens arrive in URL fragment, which browsers do not send to the server. This does not prevent page scripts from reading them; scrub still matters.
- [setSession](https://supabase.com/docs/reference/javascript/auth-setsession): accepts both tokens; expired sessions can refresh and invalid tokens fail.
- [updateUser](https://supabase.com/docs/reference/javascript/auth-updateuser): password update operates on the logged-in provider user.
- Installed `@supabase/auth-js/src/GoTrueClient.ts` `_setSession` around 3614: expired token branch calls refresh; unexpired branch calls `_getUser`, saves session and notifies SIGNED_IN. Therefore issuer precheck must precede setSession and application subscriber suppression must cover staging. `updateUser` likewise changes the provider session and can emit events. Provider failure/retry semantics must be distinguished from local UI state.

## Design challenges sent to implementation owner and coordinator

The baseline main module has static imports and mountAccount creates the root/performs worker migration before auth initialization. Capturing in a React route effect is too late for a promise to scrub before any rendering/network activity. Use the earliest synchronous head bootstrap (before external resources) or a dependency-free first entry followed only by dynamic imports. Initial HTML navigation is unavoidable; fragments are not sent with it. Erase credentials and errors even when the input is malformed, foreign, unsupported or missing; no raw fragment/query in error copy, telemetry, screenshots, console, storage, `history.state` or navigation target.

Accept exact `/auth/activate` with fragment type=invite and exactly one bounded nonempty access/refresh pair. Use a narrow allowlist for actual Supabase invite metadata, reject duplicates/unexpected credentials, query/code/recovery/signup/magiclink forms rather than guessing. Always remove query and fragment before parsing errors can escape. The clean reload state must offer a useful sign-in/new-invitation recovery rather than a broken form.

Decode only to fail closed on exact configured issuer/subject/audience/expiry syntax before setSession; decoding is not proof. Provider verification against the configured dedicated Supabase project establishes identity. Compare expected/provider/session subjects and fail closed on mismatch. Never choose provider URL/redirect/user from the fragment. A forged type=invite flag is not a cryptographic invitation proof or role authority; backend reviewer assignment remains the access gate.

Stage invite completion through the existing serialized controller with blocked SDK events. setSession must not emit an application-authenticated state before human password success. AccountProvider reacts to every published subject with account HTTP, so accidental intermediate publication is observable and consequential. Clear/replace previous-account state first; only the complete validated same-identity result may publish. Password is transient input only, no durable storage or logs. Destination is fixed `/app/content-review`, never fragment/query `next`.

Race challenge: signout/peer signout/cancel during any await invalidates epoch immediately and prevents the next provider action/session publication; a password request already dispatched cannot be undone. Preserve that limitation rather than claiming cancellation undoes a provider mutation. Cleanup must not sign out a newer account. Missing/expired/foreign grant, weak password, provider/network failure and uncertain password update each need honest recovery. An uncertain update must not silently repeat a possibly committed credential change or claim success; explain signing in with the chosen password. A known weak-password error may retry only against a retained, verified, same-subject staged SDK session (refresh rotation means replaying original tokens is unsafe). New invitation/sign-in/signout clears that staging.

UX constraints: existing Mo auth shell/tokens, Persian default/English option, labelled new-password and confirmation fields, password-manager autocomplete, visible show/hide names, keyboard focus/error announcement, loading/disabled states, no native alert/prompt. Do not expose internal issuer/project/protocol diligence in customer copy. Hosted static route must serve the same entry for this exact callback without opening arbitrary rewrites/redirects.

## Owner response / design resolution

Owner agreed to earliest first-head inline one-shot closure capture and clean replacement before external resources, including invalid payloads; fragment invite pairs only, bounded metadata allowlist, duplicate/query/code/recovery rejection. Proposed atomic controller completeInvite blocks SDK events/epoch guards setSession → getUser → updateUser → getSession; publishes only after success. Exact issuer precheck precedes configured-server verification. Known weak-password retry retains only original-grant/verified-subject staging; unknown password update asks user to sign in with chosen password. Cancellation is checked before each provider action, with already-dispatched update limitation explicit. No metadata-based grants. These decisions address the design challenges; independent validation of implementation is still pending.
