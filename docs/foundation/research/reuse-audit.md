## Source-observed mechanisms and decisions

### Content ingestion and provenance — rebuild ingestion; adapt lineage ideas

`backend/scripts/ingest_questions.py:33–50` loads a local environment file at import time and fixes corpus paths to SQE Material. Do not import or execute this script in Mitooni, even to reuse its parser. Its parsing is structured around practice/mock Markdown and legal subject mapping (`:53–115`, `:283`, `:353`, `:428`). That is not a PDF/audio/image IELTS ingestion contract.

Useful narrowly observed ideas: normalized SHA-256 over stem/options (`:209–215`), source file and question number (`:337`, `:412`, `:496`) and idempotent upsert keyed by `content_hash` (`:539–578`). This hash identifies normalized question content, not original asset bytes, legal permission or lineage completeness. Its inputs omit answer-key/explanation changes; do not use it alone as an immutable edition identity.

**Proposal:** new Mitooni intake stages: original asset byte hash and stable asset ID → permission record (Iran audience, authorised uses, external processing basis) → extraction/OCR/transcription version and page/time spans → authored test/item edition → human approval → published immutable edition. Preserve original resources locally. Distribution rights already confirmed in the charter do not need to be re-requested; per-asset provenance operationalizes that authority. External model processing is a separate unresolved boundary. Required tests: rerun produces no duplicates, changed answer keys create a traceable edition, failed extraction stays unpublished, missing source spans fail review, audio/image references survive export, and withdrawal stops new serving without destroying historic attempts.

### Authored/generated questions — adapt lifecycle, rebuild IELTS entities

`backend/app/services/generated_questions.py:1979–2024` checks source type, approval state, approval timestamp, quarantine and review status. `:2487–2532` persists generated metadata including model/prompt version, content hash and serving timestamps; `:2600–2617` links seed questions/study chunks. `backend/app/routers/generated_review.py:14–18`, `:137`, `:150–158` expose pending/approved/rejected/quarantined review and reviewer reports. These are useful state-machine and audit patterns, not proof of the originality or correctness of generated output.

**Adapt** separate draft/review/publish/quarantine states, provenance edges and versioned authoring jobs. **Reject** transfer of seed IDs, content, source snippets, explanation prompts, legal taxonomy and any prompt/examples containing licensed material. **Rebuild** IELTS test → skill section → part → group → item, accepted answers and word-limit rules, task illustrations, audio spans and writing/speaking rubrics. Mitooni already has IELTS-shaped group and attempt contracts in `web/src/api/schemas.ts`; forcing them into BarEx question rows loses information.

Human-authored questions must be first-class rather than falsely labelled generated to satisfy a serving predicate. Newly approved items must pass answer-key, rubric, media and rights validation. A publication test must demonstrate that draft/quarantined assets and answer keys are absent from both API responses and shipped browser bundles.

### Attempts, progress and recovery — adapt transactions; rebuild assessment semantics

`backend/app/routers/practice.py:246–307` verifies served-question ownership before loading an answer/explanation, then persists the attempt. This is valuable corpus protection, but answer correctness is scalar equality. Retrying its final insert has no request-idempotency guard in this function; do not assume practice retries are exactly-once.

`backend/app/routers/mock.py:632–637` checks session ownership; `:719–722` calls an atomic creation RPC; `:927–945` updates drafts only while owned/in-progress; `:1284–1301` atomically commits completion and attempt rows, returning conflict if already completed. These are **adaptable transaction boundaries**, not an IELTS schema. Draft values at `:616–625` restrict answers to A–E, while Mitooni accepts strings/string arrays, essays, recordings and per-section state (`web/src/api/schemas.ts:232–282`). Source draft update has no visible revision compare-and-swap in this route; stale tabs can overwrite newer drafts. Full multi-section timing, recording upload and asynchronous grading require new design.

**Proposal:** immutable test edition bound at creation; server-owned section deadlines; revisioned section patches with conflict recovery; client-generated operation IDs; idempotent submission returning the existing canonical result on retry; separate submitted/pending-marking/marked/failed-review states. Media must be acknowledged durably before submission. Treat vocabulary review, practice accuracy, mock scores and estimated bands as distinct progress signals. Source `backend/app/services/srs.py:1–21`, `:59–80` is a particularly small **retain/adapt** candidate: pure deterministic scheduling, no I/O. It can schedule original vocabulary cards; it is not a calibrated readiness predictor.

Tests: competing saves, expired/replayed tokens, offline/reload recovery, submit timeout after commit, duplicate submission, deadline tampering, answer-key visibility, retake history immutability, interrupted audio upload and reconstruction from persisted state. Run them against Mitooni contracts, not translated BarEx fixtures.

### AI grading and retrieval — retain safety pattern; rebuild marking

`backend/app/tools/tutor_retrieval.py:19–32` limits search/detail projections; `:574–607` searches only an approved generated selected-lead sheet and fails when the context is missing/not ready. `:663–693` allows question details only through explicit active-pack IDs or evidence that this user was served the question, then checks generated eligibility and lead scope. **Adapt** scoped, server-authorized retrieval with bounded excerpts and provenance; separate learner content from source corpus. Neither tool input supplied by the model nor a client-provided allowed-ID set should independently grant authority.

Observed search includes English `[a-z0-9]` tokenization (`:34`, `:41–58`), full-text and substring queries (`:426`, `:447`). Do not describe this code as a general bilingual vector RAG engine. IELTS/Farsi retrieval needs new language handling and evaluation; its allowed content scope should follow asset permissions and task context.

No IELTS rubric-based writing/speaking marker was established in the inspected source. BarEx practice uses answer equality; its generated-question reviewer evaluates question quality, not learner language performance. Mitooni `WritingFeedback`/`SpeakingFeedback` explicitly carry `dummy` (`web/src/api/schemas.ts:334–364`), and `web/src/mocks/scoring.ts:21–24`, `:95–100` returns fixture marking for these skills. **Rebuild** marking as versioned rubric jobs with explicit model/prompt/rubric/audio/transcription provenance, uncertainty and review status. Do not infer pronunciation from transcript text alone or turn per-part display scores into validated overall assessments.

Acceptance: domain experts label original, permitted held-out writing/audio samples; compare criterion-level agreement, systematic bias and error severity with explicit human-defined tolerances before learner-facing band estimates. Include accented speech, noisy/truncated audio, irrelevant/refusal responses, short work and prompt injection inside source/submission text. Version changes trigger regression evaluations. Schema-valid output alone is not scoring validity. A manual expert review path must remain available when AI is unavailable or unapproved.

### Coach roles and workspace — adapt engagement boundary; rebuild IELTS review

Source code inspected here is app implementation, not private coaching files. `backend/app/services/coaching.py:73–95` delegates authorization to an engagement-actor RPC. `supabase/migrations/20260923165602_coach_delivery_v1.sql:186–205` binds candidate/assigned coach, active engagement and current Guided subscription; an unrelated or revoked coach is denied. `:158–172` enables RLS/revokes client grants and protects append-only history. `:548–558` restricts RPC execution to the service role. These are strong reusable **patterns**; deployed state was not inspected.

`backend/app/services/coaching_workspace.py:219–238` uses expected plan versions; `:413–422` checks file bytes, MIME and extension; `:665–709` defaults progress sharing to no metrics and lets only the candidate change selection. `backend/app/main.py:180–185` makes coaching responses private/no-store. **Adapt** assignment history, optimistic concurrency, participant-scoped comments/resources, explicit sharing and authorization before reading upload bytes (`coaching_workspace.py:476–480`).

**Rebuild** essay/audio review queues and returned rubric feedback: Mitooni `CoachReview` (`web/src/api/schemas.ts:518–532`) is a UI projection with requested/in-review/returned status, not a staff authorization model. BarEx subscription plan ID `guided`, billing eligibility, terms, CV/photo onboarding, payouts and session accounting must not be imported as Mitooni business rules. Separate learner, assigned coach and operations permissions, and specify access to previous work after reassignment/revocation. Source file allowlist does not support IELTS audio; extend through a new private object-storage/upload pipeline rather than loosening document validation.

Tests: learner A/learner B isolation; assigned/unassigned/former coach; concurrent reassignment while writing; revoked sharing immediately removes metrics; plan conflicts; immutable review revisions; private media guessing/expiry; invalid/oversized uploads; no learner content in shared caches or logs.

### Auth and data isolation — adapt BFF, explicitly choose session protocol

`backend/app/dependencies.py:107–137` verifies a Bearer token using Auth get_user and rejects invalid/missing tokens. `:43–56`, `:140–151` use app metadata/backend allowlists for internal authorization, not editable user metadata. Local bypass requires explicit development/loopback configuration (`:59–67`). `backend/app/db/supabase_client.py:42–67` rejects hosted development database access unless explicitly overridden; retain that guard concept.

The source service client deliberately bypasses RLS (`backend/app/db/supabase_client.py:1–13`, `:70–90`). Therefore a passing RLS test does not demonstrate BFF isolation: every privileged query/RPC needs ownership/engagement enforcement. The coaching SQL takes actor IDs as arguments and is server-only; exposing the same RPC to authenticated clients without redesign would turn caller-supplied identity into an authority flaw.

Contract mismatch: Mitooni `web/src/api/client.ts:17–35` sends cookies and expects `.error`; source auth requires Bearer and typical errors use `.detail`. Mitooni `web/src/api/queries.ts:57–85` expects backend auth/OTP/Google routes. **Decision required:** a cookie-session BFF that implements those contracts, with CSRF/session controls, or an explicit frontend auth adapter. Do not silently combine protocols. The schema file uses Zod, but the fetch wrapper only casts JSON (`client.ts:35`); runtime validation must be wired into the backend boundary. Do not blindly retain account lookup responses that reveal existence/name (`queries.ts:75–80`) without enumeration review and rate controls.

### Observability and reliability — selectively adapt; add assessment-wide monitoring

`backend/app/db/read_retry_transport.py:19–39` restricts one transport retry to bodyless REST GET and excludes RPC; useful protection against replaying writes. `backend/app/main.py:247–266` adds a bounded checkout-attempt ID and logs only status/request ID before authentication. **Adapt** correlation IDs and read-only retry discipline, independent of billing. Source logging is not automatically suitable: `dependencies.py:125` logs raw auth exceptions; `routers/mock.py:1308–1310` logs learner user/session IDs and scores. Do not carry that logging policy into Mitooni without minimization.

No claim of comprehensive tracing, alerting, retention or production SLO coverage is made from these inspected paths. **Proposal:** structured events for save/submit/upload/mark/review with operation ID, test/rubric/model edition and latency/outcome; no essays, transcripts, tokens or raw model payloads in ordinary logs. Add stuck-marking detection, retry/dead-letter visibility, correlation from failed client operation to job, model cost/usage limits and an operator recovery path. Provider outage must preserve work and clearly show marking pending rather than fabricated success.
