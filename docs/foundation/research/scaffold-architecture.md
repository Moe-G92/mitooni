## Observed implementation

### Scope and contracts

`web/src/app/App.tsx:22–92` contains a substantial learner application: public pages; identifier-first authentication; onboarding; overview, practice, mocks, results and criterion feedback, progress, vocabulary, coach and settings; full-screen exam creation/execution and four dedicated practice players. It has no coach/staff application routes, content administration or server routes. Client route guards consult `/me` (`RequireAuth.tsx:7–16`); this is navigation behavior, not backend authorization.

The application is React/Vite with React Query and Zod contracts (`web/package.json`; `api/queries.ts:23–40`; `api/schemas.ts`). `api/client.ts:17–35` sends cookie credentials but merely casts response JSON to TypeScript generics: it never parses the Zod contract at this boundary. `queries.ts:44–228` covers learner operations, attempts, recordings, results, vocabulary, coaching and notifications. `docs/handoff/api.md` describes these same shapes, but is insufficient as a production specification: it lacks request limits, ownership, permitted transitions, concurrency policy and asynchronous assessment states.

`main.tsx:10–15` starts browser MSW unless `VITE_USE_MOCKS` is exactly `false`. `mocks/browser.ts` deliberately gives newer auth handlers precedence over duplicate old handlers. `vite.config.ts` supplies an optional development-only API proxy. A production build is not evidence of a deployed real backend; mock mode is the default, including for a build without the explicit flag.

`mocks/db.ts:10–46` stores a single profile and all attempts/results/reviews in one process cache backed by localStorage `bw-db`; version mismatch or parse error replaces it with demo data. Accounts are identity labels, not separate owned databases. `persist():50–56` swallows storage quota/blocked-storage failures, keeping only an in-memory session. The mock can therefore report saved while durability is absent.

### Attempt state, time and recovery

`mocks/attempts.ts:9–46` creates all section states and copies accommodation. `api/schemas.ts:244–282` exposes mutable section status, remaining time, answers, essays, recording references, timestamps and navigation; `SectionPatch` is the whole section made partial. No content revision, attempt revision, owner, operation ID or explicit deadline exists.

`exam/engine/session.tsx:147–185` batches whole persisted section snapshots after 400 ms, sends them to `saveSectionState`, and attempts a flush on unmount. This is useful prototype behavior but does not prove crash-safe autosave. The flush sets pending to null before the request, has no single-flight queue or expected revision, and can overlap subsequent requests. A delayed older save can overwrite a newer snapshot. A failed flush restores pending state but schedules no autonomous retry; the next user action may trigger one.

**Blocking correctness defect:** `session.tsx:152–165` catches save errors without rejecting. `pages/exam/ExamPage.tsx:110–113` awaits that flush and then submits the section regardless. It can submit stale answers while the client still holds unsaved work. Existing pending/in-flight requests also are not joined by a second flush, so awaiting flush alone does not create a save barrier. `leave():148–153` navigates after this same non-failing flush. A new production implementation must fix both the client barrier and transactional submission semantics.

`useCountdown.ts:19–40` derives display time from `Date.now()` while mounted, avoiding simple interval drift; `ExamPage.tsx:120–135` saves approximately each ten seconds and auto-submits at zero. However, reload starts from persisted `remainingSec`, and closing the browser pauses elapsed time indefinitely. Listening explicitly starts its clock after Play (`ExamPage.tsx:101,158`; `ListeningSection.tsx:72–80`), including on resumed attempts; its resume offset is inferred from saved remaining time (`ListeningSection.tsx:61–69`). The mock server never checks deadlines (`handlers.ts:158–174`). The handoff's recommendation that a server own time is sound but not implemented. Exact learning/exam pause, accommodation and interruption policy is a domain decision, not something to copy from this prototype.

`handlers.ts:195–222` marks whichever section ID is provided as submitted and increments `sectionIndex` on every request, even a repeat or non-current/unknown ID. Repeating final submission rebuilds a result and notification. It is not idempotent and has no legal state transition check. The handler ignores saves to submitted sections but otherwise accepts the client-shaped patch (`158–174`).

### Recording boundary

`SpeakingRoom.tsx:395–413,470–503` keeps question takes and their blobs in React memory. `575–590` joins and uploads them only at final submission. Reload/unmount before that point loses recorded takes; persisted current-part navigation does not restore stage, question index, prep notes or unsent audio. `436–447` stops recording and releases object URLs on leave without preserving chunks. The README's general claim that reload resumes every answer is therefore materially incomplete for Speaking.

`media.ts:12–20` requests audio only and turns permission/device errors into a boolean; real browser/OS-denial, interruption and device loss need explicit recovery. `recorderMime():49–54` allows WebM, MP4 and Ogg. `joinAudio.ts:35–55` normally emits WAV for multiple takes and otherwise concatenates raw containers on decode failure, which does not establish a valid playable media file. `queries.ts:150–154` always names the upload `.webm`, although its actual MIME may differ. The written API describes WebM/MP4, omitting actual WAV/Ogg possibilities.

`handlers.ts:225–246` stores the final blob in IndexedDB, with a timestamp key and unchecked client duration; it accepts a blob even for an absent attempt, has no MIME/size/duration/part/ownership/submission validation, and retrieves by key without authorization. Discard deletes the attempt (`150–154`) without deleting its recording blobs. Private server storage, durable upload states, validation and retention/deletion behavior are entirely new work, not a swap of persistence primitives.

### Content, assessment and coaching

`mocks/tests.ts:70–126` creates a full Academic test, section variants and practices from the same source groups. These are useful navigation fixtures, not independent unseen assessment forms. `stripAnswers():151–173` removes item keys/evidence but preserves `part.audio` wholesale, including the transcript defined in `schemas.ts:157–161`. Even aside from complete fixture keys shipped with MSW, an exam API copying this projection would disclose Listening transcripts. Use separate learner-delivery DTOs with positive field allowlists, not redaction of a rich authoring object.

`mocks/scoring.ts:95–128,148–172` uses canned Writing/Speaking bands and transcripts with `dummy: true`, then incorporates those bands into the overall score. The dedicated Writing practice screen also explicitly uses canned feedback (`pages/practice/WritingPractice.tsx:12,42–52,231–266`); merely connecting `/attempts` does not replace every simulated feature. `Result`/`SkillScore` require numeric bands (`schemas.ts:380–410`) and have no pending, failed, reviewed, provisional or unavailable assessment representation. This makes honest asynchronous marking a contract change. A boolean `dummy` alone is not adequate provenance or human review history.

`handlers.ts:325–393` serves shared slots/reviews, flips booked state and manufactures delayed coach replies. `schemas.ts:514–532` defines a slot with no coach/learner/timezone ownership, and reviews with no assignee, artifact revision, delivery/marking revision or audit trail. The UI can request an essay/recording review (`Coach.tsx:24–77`) but no staff work queue or marking action exists. `Coach.tsx:559–563` upgrades the profile plan directly; `PATCH /me` merges any `Partial<Profile>` (`handlers.ts:78–84`), including IDs/plan. In production, learner-editable preferences and server-controlled identity/entitlements must be separate schemas.

### Authentication/security

`auth-handlers.ts:13,54–89` accepts any password, any six-digit OTP and a dummy Google flow. The mock auth state is a local boolean; there are no real sessions, recovery tokens, password handling or verified contact identity. Lookup returns existence plus name (`47–51`), creating enumeration/privacy behavior if reproduced; rate limiting alone does not remove the disclosure. Most attempt, recording, detail-result, vocabulary and coach handlers omit even the mock signed-in check. These are prototype limitations rather than evidence of a reachable production incident, but copying these rules is unsafe.

Required server foundations include authenticated identity, authorization per learner/assigned coach/artifact; allowlisted mutation fields; bounded input and upload validation; cookie/CSRF/origin policy appropriate to the chosen deployment; rate-limited authentication and expensive operations; private media; redacted logs; retention and deletion. Infrastructure/dependency vulnerability status was not verified in this assignment. No `.env` was read and no secret audit result is claimed.

## Proposed foundation and alternatives

**Preferred proposal: retain the learner scaffold, introduce a small modular backend and upgrade contracts before feature expansion.** Use one deployable application boundary initially, with explicit identity, content delivery, attempts, private media, assessment and coaching modules. One relational transactional model and an abstract private blob store suffice conceptually; provider/hosting selection is deferred. Frontend hooks remain useful adapters, but the claim that no screen changes are needed is false for error recovery, asynchronous marking, entitlements and coach operations.

Alternative A, copying the mock contract exactly into a server, is superficially quickest but preserves client authority, unsound transitions and missing ownership. Reject it. Alternative B, full fork of an established tutor, may reuse mature auth/jobs/coaching machinery, but would bring domain assumptions, migration/dependency burden and licensed/private content risks; this assignment has not inspected that source and cannot endorse its maturity. The reuse specialist must establish actual source/revision/fit. Selective extraction of verified infrastructure is compatible with the preferred proposal; wholesale fork needs evidence that the saved work exceeds IELTS-specific adaptation and validation costs. Alternative C, building a new full platform and UI, discards a substantial existing interaction model without evidence that doing so solves the foundation risks. Defer unless independent validation exposes non-local structural defects.

### Contract decisions required before implementation

- Pin `testRevision`, immutable asset hashes/provenance and rubric/scoring revision on every attempt/result/review. Content edits create new revisions; an old attempt always resumes and scores against its original revision. Territory/rights basis belongs in the content administration record, not learner UI.
- Separate authoring/key/transcript content from delivery DTOs; return only authorized content needed at the current stage. Keep results/review disclosure explicitly gated. Runtime-validate requests and critical responses with shared generated schemas; version the API/contracts and tolerate older persisted client drafts deliberately.
- Model attempts as explicit server transitions: created, section active, section submitted, attempt submitted; assessment independently pending/running/returned/failed. Store server start/deadline and clock policy. Client remaining time is display-only, never a trusted mutation. Define whether interruption consumes exam time and how practice pause differs before tests are written.
- Give save operations a client operation ID and expected section revision. Acknowledge authoritative revision/server time. Serialize client writes; reject stale revisions with a recoverable conflict response. Adopt one active writer per attempt initially, detect a second tab/device and offer explicit takeover; do not silently last-write-win essays. Keep an acknowledged/queued distinction and retryable local outbox. Local draft retention requires an explicit expiry/sign-out policy because essays/audio are personal data.
- Submit with an idempotency key and expected saved revision, atomically freezing the final snapshot and transitioning the current section once. A duplicate returns the same outcome; conflicting submissions do not advance the index. Persist result/marking job plus an outbox event transactionally; consumers deduplicate by job/event ID. Do not require exactly-once network delivery.
- Persist each Speaking take promptly with a manifest, content checksum, sequence/question ID and upload status. Resume must reconcile local and server manifests. Validate actual container/MIME/size/duration; keep originals, assemble/transcode on a controlled path and mark media ready only after decode verification. Finish must refuse an incomplete required upload or present an explicit domain-approved incomplete-submission choice; never show lost audio as successfully submitted.
- Use immutable response/recording snapshots for expert review. Assign a reviewer, enforce assigned-coach permissions, store rubric version, feedback revision, author and return time; separate learner messages from authoritative feedback. A human review queue and a minimal staff return-feedback action are first-pilot foundations. Automatic marking can be added behind the same assessment interface only after its separate validity/privacy/provider gates pass.
- Keep learner profile preferences separate from accommodation approval/entitlements if those require operator authority. Pilot entitlement can be explicitly assigned manually by an authorized operator; no purchase flow or invented price is required. Atomic slot reservation needs a uniqueness constraint and idempotent retry; cancellation must check ownership and policy. Never use fixture replies or direct plan PATCH as pilot delivery.
- Production must fail closed if mock mode is requested or backend configuration is absent. Demo runs on an explicit separate build/origin, uses synthetic accounts and visibly sample scoring, and has no production cookies/data. Production assets must exclude fixtures, answer keys, mock worker and dev/reset flows. Test the built artifacts and deployed configuration, not only environment variable intent.

8. Expert can open the exact frozen response/media, return criterion-linked feedback, and learner can distinguish pending/failed/returned and machine/human provenance without canned bands. Feedback revision does not mutate original submission or erase previous expert feedback.
9. Existing tests remain useful and pass after schema adapters change; add independent server integration and browser failure tests. No live user data, provider calls or paid infrastructure are required to prove the local architecture slice. Pilot usability/accessibility/performance and learning/marking validity are separate gates, not inferred from these checks.
