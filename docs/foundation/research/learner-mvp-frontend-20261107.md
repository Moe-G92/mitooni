## Existing real study mechanics: keep and extend

`account/study/contracts.ts` gives strict schemas for pinned bundle/objective/rubric/policy versions; a journey with revision and available/completed/locked steps; workspace/draft/attempt identity bindings; explicit supported/independent conditions; canonical paired tutor messages and evidence citations; proposal acceptance; durable turn status including dispatch-unknown. This is a substantially stronger foundation than the prototype hooks.

Current narrowness is explicit in source: journey skills are only reading/writing, workspace task kinds only reading/task2, response only free text, raw check exactly one deterministic item. There is no lesson-body/teaching-sequence projection, multi-item answer map, learner media binding, four-skill mock lifecycle or progress/history endpoint in these frontend contracts. A polished plan cannot conjure these data structures from existing DTOs.

`StudyClient` calls `/study/journey`, workspace resolve/read/draft/assistance/child attempt, submit, tutor turns/poll/cancel and proposal accept. It uses `GuardedTransport`, per-operation keys, expected revisions, deadlines, owner assertions and strict response validation. `StudyWorkspace` protects unsaved work, renders English task content LTR, offers supported/independent mode consent, and task/tutor pane selection on mobile. `useWorkspace` retains the right place for exact-operation retry and canonical reload. Preserve these protections when adding rich task controls.

The existing reviewer media path is intentionally narrow: `GuardedTransport.rawResponse` only permits `/content-review/targets/…`; `review/media.ts` binds package/target hashes, verifies MIME/signature/hash and bounds bytes. Reuse byte-validation/object-URL cleanup patterns, but create a distinct learner media contract. Widening this regex or sending candidates to reviewer routes would cross the role/content boundary. `review/speakingContracts.ts` contains useful qualitative evidence/insufficient-evidence and recording-binding shapes, but these are review DTOs, not an existing candidate permission.

## Proposed product composition and transitions

Decision requested: extend the configured account app with Mo presentational components and typed receiving adapters; preserve prototype as reference. Rejected alternatives: mounting the entire prototype router would restore simulated auth/scoring and violate the import boundary; using the review catalogue as candidate home misses the learning outcome; importing a BarEx shell contradicts Mo's authority; creating a third complete frontend duplicates existing working account/session protections.

Proposed path, with content IDs supplied by server rather than hardcoded browser navigation:

1. Sign-in → account admission → existing onboarding if incomplete. Successful onboarding opens `/app`, not Settings. Access-required accounts remain denied; the current three review accounts do not imply candidate access.
2. Today (`/app`) answers “What should I study next?” First block is next/resumable lesson with one Continue/Start action, then a compact week plan and truthful completed-work summary. New candidates see actual first published lesson, never a predicted score or compulsory full mock to unlock all study.
3. Plan uses Mo's weekly composition, backed by server journey/schedule. Each block opens a stable content/attempt binding. Replanning is explicit and revisioned; completion or accepted tutor proposal refreshes the same source of truth. The existing `/app/coach` route can house this established plan composition while optional human coaching is a distinct available action, pending coordinator naming decision. Avoid confusing AI tutor, plan and human coach as one entitlement.
4. Lesson workspace (`/study/:workspaceId`) shows teacher-designed explanation/example → guided practice → independent transfer → feedback/revision in the same Mo frame. Desktop content/work/tutor layout, phone one primary pane at a time. English IELTS content remains LTR inside Persian chrome; tutor language follows preference where supported. Lesson sequence is actual content payload, not a transcript invented by the client or a PDF catalogue.
5. Practice (`/app/practice`) shows real published four-skill activities and prior evidence. Selecting one resolves or resumes work atomically. Current standalone `/practice/:skill` prototype pages become optional presentation components under the real attempt route, not parallel hidden local state stores.
6. Submission freezes versioned work, then result detail shows available deterministic checks immediately and qualitative/human feedback when completed. User can revise into a child attempt and return to next plan action. Missing provider must show unavailable/recovery, never a canned “AI” success. Without provider provisioning the product may be implemented and locally validated, but the full live tutor outcome cannot be declared operational.
7. Results/history and Progress show server-owned completed attempts, dates, conditions and evidence, with a direct reopen/review path. For a first account, small/empty evidence is honest; no aggregate overall band before a valid full assessment.
8. Mocks (`/app/mocks`) lists actual published tests with available skills/duration. Device/sound checks → server-issued attempt → timed section sequence → durable submitted result. A section-only or incomplete test is labelled accordingly. Full mock must not silently substitute practice/drills or fixture productive-skill marks.

Do not expose authoring stages, internal corpus labels, checkpoint verdicts, worker names or reviewer workflows as candidate copy. Preserve essential task instructions, recording consent, errors, assistance effects and assessment limitations; remove generic secondary labels/taglines rather than discard meaningful instructions.

## Contract additions needed before frontend implementation

These are proposed contract requirements, not claims that backend already provides them. Exact endpoint names and schemas require coordinator/backend agreement.

- **Admission/capabilities:** existing account membership stays server-owned; distinguish candidate study/practice/mock/media/feedback access and reviewer role. Capabilities include actual feature/provider availability. The client cannot enable study by profile plan mutation.
- **Home/plan projection:** account-scoped journey/schedule revision, goals and budget; ordered next/resumable step, skill/stage, duration, stable content/edition, availability/lock reason, exact resume target and evidence basis. Scheduling is server-owned; client groups/labels dates only.
- **Lesson projection:** published unit/version/objective, bilingual chrome/title as available, English teaching blocks, examples, safe media descriptors, activity kinds, progression checks and permitted support conditions. No private authoring source index, unpublished corpus, model prompts, answer keys or reviewer rationale fields in the candidate DTO.
- **Attempts:** answer-kind discriminated payload (text, option(s), match, gap(s), essay, recording reference); expected draft/attempt/content revision; durable save acknowledgement; repeat-safe create/submit/revise and canonical conflict response. Server validates item identity, upload references and publication. Server deadline/current section owns final timing; client countdown is display only.
- **Checks and feedback:** server-authorised check/reveal policy, exact workRef/version, correct/total only for relevant deterministic items, qualitative observations/action/evidence with queued/running/failed/unknown/ready states; teacher review as separate provenance. Numeric bands require a distinct validated assessment type. No overall from missing productive-skill marks.
- **Learner media/recording:** authenticated snapshot-bound GET and attempt-owned upload/finalise, content type/byte/duration limits, integrity binding, revocation and object-URL lifecycle. Record only after explicit action; permission denied/device absent/unsupported codec/empty take/oversize/offline upload each has recovery. Existing review recording API is not an eligible substitute.
- **Progress/history:** server aggregates scoped by skill, activity kind, assessment conditions and versions; completion/accuracy/feedback/band fields separated, evidence count/window included; paginated actual attempts. One stored value feeds repeated summaries/chart/table.
- **Optional vocabulary/coaching:** only implement enabled services against real ownership and failure contracts. If required for first complete MVP, receive explicit backend/service work; static placeholders or simulated upgrades do not satisfy acceptance.

Security admission hazards found in actual source: `api/schemas.ts` prototype question items include accepted answers and explanations; never serialize that whole `Test` into candidate pre-attempt state. `exam/widgets/Figure.tsx` fetches a public SVG and inserts it with `dangerouslySetInnerHTML`, justified only by its current own-static-assets assumption.
