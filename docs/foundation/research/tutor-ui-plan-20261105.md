## Chosen bounded journey and routes — proposed

1. Ready member opens `/app`: Mo Today frame displays the current server-planned objective and primary Continue action. No score/trend row. If no suitable published work exists, show an honest empty state with an available choice, not a generated assessment.
2. `/app/practice`: Mo's room/catalog composition lists actual allowed Reading and Task2 objectives. Learner may choose support, available standard work or an actually available challenge. Plan choice is an explicit CAS server decision; UI does not grant itself a next stage.
3. Proposed `/study/:workspaceId` uses an adapted Mo PracticeShell outside the sidebar, preserving existing full-screen work intent. Breadcrumb/exit returns to actual Today/catalog. The workspace resolves its own task kind and pinned versions from the server; URL cannot select arbitrary content/rubric or actor. Deep-link authentication requires an explicit receiving redirect-allowlist addition with strict ID/path validation, reviewed with security; current allowlist is not broadened by this plan.
4. Desktop/tablet: retain Mo's English task/editor main column and340–400px secondary column; the secondary column is the AI tutor/feedback/planner-action surface. The AI first orients/explains against approved anchors, asks a purposeful check, waits for the learner, then grounds feedback and asks for repair. The passage/editor remains usable while tutor loading fails; that is recovery, not a replacement static-product direction.
5. At360px: one Task/Tutor pane at a time using accessible tabs; the task/draft/controller stays mounted and controlled so tab switches do not clear work or restart a turn. Preserve explicit Save/Submit and pending state near the work; one primary action per stage. No extra “Tutor” top-level nav item or generic dashboard is needed.
6. Learner submits frozen work, receives released deterministic Reading raw accuracy or qualitative AI formative feedback bound to that submission, repairs/revises, then chooses a server-validated next action. Writing revision is a child snapshot; no overall band or mastery badge. Optional human review appears only if the server reports an actual authorized service/assignment/status; otherwise no fake coach response, booking or turnaround promise.

Persian fresh UI and English option remain; task text/essay fields are lang=en/dir=ltr inside the RTL frame. Tutor messages carry explicit content language/direction. Keep Mo typography, skill colors, cards and hierarchy. New secondary copy is limited to essential save/error/help-condition/provenance states; internal policy enum names and review labels are not customer UI.

## Contract proposal with backend owner

Backend design at `tutor-backend-design-20261105.md` now specifies these receiving endpoints; UI design substantively agrees after resolving draft-ID/admission/help-switch gaps:

- GET `/api/study/journey`: metadata-only owned steps/capabilities before admission, no protected task/anchors.
- POST `/api/study/workspaces/resolve` `{stepId,conditionPreset:"supported"|"independent",expectedJourneyRevision}`: atomic admission creates/resumes the owned workspace plus OPEN attempt, stable server draft ID and context manifest before any task release. Only matching open conditions resume; a different condition/context gets409 rather than silently reusing a taught thread. Preset is a request, not official exam format, timing policy or evidence-purpose authority.
- GET `/api/study/workspaces/{id}`: exact owned run/context/draft/attempt/turn; PATCH its `/draft` with `{expectedDraftRevision,taskId,changes}` saves only the current OPEN draft.
- POST `/api/study/attempts/{id}/submit` `{expectedWorkspaceRevision,expectedDraftRevision,expectedConditionsRevision}` freezes already-admitted work once; it does not first admit independence after the learner has seen content.
- POST workspace `/assistance` `{expectedWorkspaceRevision,expectedConditionsRevision,action:"switch_to_supported"}` is an explicit learner-only command before hints. It irreversibly downgrades current conditions, appends history and binds a supported context without erasing the restricted one. No model tool/intent can provide that consent.
- POST workspace `/attempts` after submission `{parentAttemptId,expectedWorkspaceRevision,conditionPreset:"supported"}` creates a child draft/attempt for revision. Closed work remains immutable; same-family revision cannot become fresh independent evidence.
- POST workspace `/turns` `{expectedWorkspaceRevision,workRef:{kind:"draft"|"attempt",id,revision},intent,message}` returns202 Turn after durable admission. Draft id is a real server ID, not guessed workspace identity. Intent allowlist explain/hint/feedback/propose_next; feedback requires an owned frozen submission and permitted context. One active turn per workspace; same operation returns same turn.
- GET `/api/study/turns/{id}?afterSequence=N` polls persisted allowlisted events/canonical status. Reconnect never re-POSTs generation. Without a cursor it returns200 bounded canonical snapshot {turn,events:[],cursor:lastEventSequence,workspaceRevision,terminalMessage}. Only an explicit invalid/ahead/expired cursor returns409 snapshot_required with reload_turn_without_cursor. Public events are accepted/started/tool_status/completed/failed/canceled/dispatch_unknown, never raw text/candidates. Completion resolves the committed terminalMessage, never promotes client partial text.
- POST turn `/cancel` with expectedTurnRevision and POST proposal `/accept` with expectedJourneyRevision are explicit guarded commands. Cancellation is requested/cooperative, not a promise of immediate provider stop or refund.

Required server entitlements are study:use for work, tutor:use for paid-capable tutoring and study:independent for restricted admission, each additionally constrained by policy/exposure. A valid identity/profile:write does not grant them. Only trusted local fixtures can provision synthetic study grants. Missing provider503 cannot become canned success. `dispatch-unknown` is an interrupted/uncertain turn: check canonical status, never auto-dispatch; a server-authorized new response is a distinct attributable operation. This is design agreement, not executed API/SDK evidence.

Required projection fields: authorized workspace ID/revision; task kind and pinned pack/objective/content/rubric/policy IDs+versions; actual allowed actions; pedagogic stage; attempt ID/current work revision/frozen submitted revision; active turn ID/status; released messages/evidence; evidence-use/help condition; next-action proposal with expected revision; actual human-review capability/status. Hidden keys, private rationale, sealed families and server-only context manifest must never appear in learner DTOs.

Every mutation uses the existing captured account subject/epoch, UUID operation key and expected workspace/work revision. Acknowledgment distinguishes saved work from pending model execution. Retry same operation preserves exact key/body/revision; new content creates a new operation. Structured403/409/422/503 and requestId retain user work and make recoverable versus forbidden explicit. No cookie/client-side role fallback.

## UI state and recovery contract

| Independent axis | Display/behavior |
| --- | --- |
| Binding/bootstrap | Quiet Mo loading frame until this workspace/version resolves; no flash of another/empty tutor thread. Timeout offers fetch/rebind retry only |
| Work dirty / saving / saved / save failed | Local editor shows actual state. First bounded slice may use explicit Save plus mandatory save-before-submit/send; never imply unsaved keystrokes are durable. Submit is blocked until exact work revision acknowledged. A pending save locks its submitted fields or preserves subsequent edits separately; never clears newer typing |
| Generation queued/running | Tutor composer prevents duplicate send while one turn active. Proposed first-slice release policy buffers raw model text internally and exposes safe generation status only until validation; editor remains available as policy permits. No feedback/progression inferred from running state |
| Generation disconnected/interrupted | Keep last saved task/work and safe interrupted/pending status. Reconnect requests the same turn after the last accepted sequence; dedupe by turn ID+sequence and use canonical completion. No raw buffered text release or automatic duplicate model call |
| Generation failed/invalid output | Preserve work, clear busy latch, offer explicit allowed retry/new operation after canonical status proves terminal failure. Missing citations/invalid state proposal yields unavailable/abstain, never fabricated success |
| Completed turn | One canonical message/feedback record, bound to exact task/attempt/work revision. Duplicate terminal event does not append another answer or repeat next-step commit |
| Version conflict | Preserve draft; show canonical version and explicit discard/reload or reviewed rebase choice. Do not silently overwrite. Same-family revision remains development evidence |
| Session loss/member revocation | Stop polls/send/save, purge private UI via existing epoch boundary. Reload requires deliberate sign-in; resume only server-owned acknowledged work. Never replay A's pending draft/action under B |
| Content withdrawn/branch absent | No new start; show actual safe available alternatives. Existing work retains attribution/affected-state flag. Do not generate substitute marked content |
| Human review pending/unavailable | Separate from AI generation and saved work; waiting does not freeze unrelated allowed learning. No inferred human provenance or promised service |

Independent attempt: render only permitted control/task help. Asking substantive help opens a concise explicit switch action before any hint is requested/released; only server-acknowledged switch exposes tutoring and changes evidence use to supported. Declining preserves the independent attempt. A sealed evaluation may disallow the switch. A fresh chat cannot reset family exposure. These are server invariants, with UI providing meaningful choices rather than policing content itself.

## Reopened release contract — generated qualitative tutoring

The earlier IDs-only teacher-phrase projection is superseded. It may support explicit deterministic engineering fixtures, but cannot stand in for the real tutor or silently become a production-success fallback. The product uses the reused Agents SDK to generate qualitative explanation, questions, observation and repair feedback within teacher-authored objectives and policy.

Raw model text/candidates remain private until reference/structure/policy checks and terminal persistence succeed. Public polling exposes only safe generation status before commit. Reconnect retrieves the same canonical turn; failure/refusal/cancellation/dispatch-unknown exposes no buffered body. No unvalidated token stream is displayed. This protects the release boundary without claiming that final validation proves every free-text statement is correct.

Exact amended backend terminal DTO: `{id,turnId,workspaceId,kind:"explanation"|"question"|"feedback",text,citations:[{anchorId,label}],workSpans:[{start,end,quote}],observations:[{criterionId,text,workSpanIndexes}],proposalId:null|string,provenance:{actorKind:"ai_formative",runnerKind:"provider"|"synthetic",bundleRef,contextManifestId,workRef:{kind,id,revision}},createdAt}`. Server supplies IDs/labels/provenance. Private anchor bodies, provider IDs, tools and reasoning remain absent. Bounds: text6000 codepoints,8 citations,8 spans of at most600 codepoints each,8 observations of at most1000 codepoints each, server labels120 codepoints and total public JSON32KiB. Oversize is rejected before commit, not truncated into an apparently complete message.

Citations resolve only server-approved currently authorized anchor metadata; work spans must exactly match captured immutable work. They do not authorize hidden answer keys or imply semantic entailment. Observation criterion IDs come from the pinned rubric; there are no numeric-scoring fields. `terminalMessage` remains null unless validation and commit succeed. Flagged/uncertain/failed validation and refusal release no body. UI runtime validation enforces the same DTO bounds and fails closed on unknown kinds; message/provenance workRef must match this owned workspace and canonical turn.

Mo tutor pane renders generated strings and quotes as React plain text, never HTML, Markdown links, embedded actions or tool instructions. Citation controls are constructed only from validated anchor references; proposal controls only from the typed server-authorized proposal, never parsed from prose. Generated feedback is visibly AI-origin through concise provenance attached to the message and attributed to the exact submission; it is not expert review or calibrated band evidence. An invalid/unavailable response preserves the learner draft and offers only canonical allowed recovery. Completed messages announce at semantic boundaries; no per-token live announcements or forced scrolling.

Supported learning may explain and infer within the approved objective; assistance/exposure is recorded. Private keys stay access-controlled rather than relying on a prose filter. Independent attempts expose no tutor/model context before the explicit learner help switch or permitted post-submit review; generated text cannot silently change evidence conditions. All-level suitability still comes from real published options/policy, not invented tasks or score predictions. Synthetic catalogs remain engineering-approved only, not teacher/domain-approved.

Required negative tests cover unauthorized/missing anchor IDs, incorrect/out-of-range work spans, criterion mismatch, invalid action/progression, forbidden scoring fields and candidate failure/reconnect: no terminal body before successful commit and no partial release afterward. Generated prose can still be wrong despite structural checks; teacher review and later grounded-output evaluation remain necessary, and no universal semantic-safety guarantee is claimed. This is the same small Mo-native workspace/polling architecture, not a new browser framework or model loop.

Renewed learning agreement covers P1–P4: meaningful Reading misconception/correct paths, Writing sparse/revision feedback, and novice/Persian/advanced suitability evaluation, not fixed phrase selection. Security agreement explicitly supersedes IDs-only and requires honest prose-policy false-positive/negative evaluation without semantic-perfection claims.
