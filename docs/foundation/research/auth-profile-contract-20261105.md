## Smallest slice and registration policy

Add one account-bootstrap read, one existing-profile patch and one initial-onboarding completion command. Use BarEx Auth-only browser Supabase SDK plus verified Bearer BFF. No cookie façade, payments, coach administration, identity-email update, OAuth/SMS feature expansion or auto-enrol endpoint.

**Local/synthetic policy:** memberships are pre-provisioned by a trusted local fixture script keyed by configured issuer and synthetic subject UUID. A valid Supabase user, profile row, email match/domain, Auth user metadata or caller-supplied role never creates membership. No invitation token/registration API in this slice. Future pilot admission can be invitation-only but needs a separately implemented one-use, subject-bound admission flow; do not imply it exists. Synthetic fixtures include active learner A/B, inactive learner and verified nonmember. Fixture verifier/seed tooling is test/local-only and cannot be registered by production startup.

Member state is `none | active | inactive`; `none` is absence, not a persisted grant. Active member without a complete profile is `setup-required`; active member with accepted onboarding profile is `ready`; inactive/no membership is `access-required`. These states control routing, not invented subscription promises. Revocation takes effect on each account/content/write request regardless of JWT freshness.

## Endpoint contract

All account/profile responses and errors: `Cache-Control: private, no-store`, `Vary: Authorization`. Server resolves issuer from explicit verified target configuration and subject from verified Auth response; it never accepts either as authority from body/query/header. Existing `/api/me` keeps `{id,email}` and no membership claim.

**GET `/api/account`**, Bearer required, no writes: return `{identity:{id,email}, membership:{status,roles,entitlements}, state, profile}`. Identity email is verified provider state and nullable. For none/inactive, return empty roles/entitlements and `profile:null`; no automatic insert or inherited BarEx access. For active members, return server-owned role/entitlement arrays (initial synthetic policy only learner + `profile:write`, not paid/coaching promises), plus nullable profile. Read membership/profile in one consistent database transaction. Never return an Auth app_metadata blob or source billing data.

**Profile projection when present:** `{name,locale,theme,targets,testDate,currentLevel,weeklyHours,showFlag,notifications,onboarded,revision}`. `currentLevel` is explicitly a learner self-report, not measured proficiency; targets are goals. Identity id/email stay outside profile. `name` trimmed 1–100 characters, locale `fa|en` default `fa`, theme `system|light|dark` default `system`, targets five half-band numbers 0–9, testDate valid ISO date or null, currentLevel half-band 0–9 or null, weeklyHours integer 0–60, showFlag boolean, notifications `{email:boolean,reminders:boolean}`. Notifications here are stored preferences only; no emails/reminders are activated. `revision` positive integer and `onboarded` are server-owned. No fabricated goals/name: before initial completion profile is null and onboarding works from its own account-scoped form draft.

**POST `/api/profile/onboarding`** body `{expectedRevision:0, profile:{name,locale,theme,targets,testDate,currentLevel,weeklyHours,showFlag,notifications}}`; require active membership and `profile:write`. Strict schemas reject all other fields, including nested unknowns. Defaults apply only to omitted optional preferences, not name/goals. In a transaction: lock membership, verify active/permission, insert complete profile if absent, set `onboarded=true`, revision=1, commit. Return canonical Account projection. Existing profile with a different operation returns409. There is no client-controlled `onboarded` patch. Incomplete onboarding drafts can remain visibly unsaved browser state in this first slice; do not claim server save before completion. Durable draft onboarding is a later extension if needed.

**PATCH `/api/profile`** body `{expectedRevision:N, changes:{...allowed editable fields}}`; existing complete profile and active membership required. Allowed: name, locale, theme, targets, testDate, currentLevel, weeklyHours, showFlag and notification subfields. Nested objects merge only explicitly present fields after strict validation; null is allowed only on documented nullable fields. Reject empty changes, id/email/issuer/product/role/plan/entitlement/accommodation/revision/onboarded/createdAt and all unknown keys. Conditional write with matching revision increments once and returns canonical Account. No profile/user IDs in route/body. `email` changes require future provider-specific identity recovery/reverification, not this endpoint.

Mutations require `Idempotency-Key` UUID and `X-Expected-User-Id` matching verified subject (a safety assertion, never authority). Store operation outcome keyed by product+issuer+subject+route+key and canonical request hash. Repeated same operation/payload returns the same committed logical outcome; key reuse with different payload409. Check current membership before replay, so revocation denies even a previously successful request replay. Snapshot outcome may be older than latest revision; clients never overwrite newer cached revisions. No blind automatic retry with a fresh key.

Stable errors for new endpoints: `{detail:{code,message,fields?},requestId}` with bounded generated request ID and sanitized field-path/code entries only; no raw validation input, identity/token/provider errors. Codes:401 `unauthenticated`;403 `membership_required|membership_inactive|permission_denied`;409 `profile_conflict|account_changed|idempotency_conflict`;422 `invalid_request`;503 `authentication_unavailable|store_unavailable`. Auth foundation currently maps SDK failure to401; before integration distinguish rejected/expired credentials from transport/provider unavailability so network failures do not force logout. Existing `/me` string-detail compatibility remains during this bounded transition; Mo parser must support both until migrated. Never trust query/body identity overrides.

## Schema, grants and transactional boundary

Proposed private schema `mitooni_app`: membership composite PK `(product_id,issuer,subject_id)`, product constrained `mitooni`, state active/inactive, server-only roles/entitlements, membership revision; profile same composite PK/FK, typed preference columns or constrained JSON for targets/notifications, positive revision, timestamps and completed-onboarding state; mutation-operation table composite owner+route+key uniqueness, payload hash and bounded canonical outcome. Index exact identity lookup through primary keys. Do not reuse source `profiles`, subscriptions, Auth user_metadata or source customer identifiers.

RLS enabled on all tables, no public/anonymous/authenticated table/schema privileges, no public RPC/SECURITY DEFINER exposure. BFF uses a receiving-workload role with required SELECT/INSERT/UPDATE only; membership seed/admin role is separate from the normal profile route role. A service-role integration still bypasses RLS, so application authorization and composite predicates remain mandatory. Local integration should test both grants and app-level denial; direct DB connections test caller role semantics, not magical `auth.uid()` behavior. No browser Data API data access. In eventual shared Supabase project, issuer alone does not establish tenancy and private schema/grants must be verified against actual API exposure; no live assumptions here.

Mutation transaction locks membership row before profile/operation rows, consistent order; membership revocation takes conflicting lock. Profile updates use CAS revision; onboarding uses unique owner key plus transaction. A revocation that commits first prevents later mutation; an already committed allowed write remains historical. GET/account returns a consistent snapshot. Signout does not delete profile. React/browser lifecycle and backend restarts cannot erase acknowledged profile state.

## Frontend coordination and account races

Frontend specialist agrees account bootstrap + strict mutation split; Mo brand/layout stays intact. Replace `useMe():Profile` with typed `useAccount()` and an explicitly complete profile projection only for ready state. Settings email/accommodation become read-only/server-managed for this slice; do not silently continue accepting them. `plan`/accommodation are separate future server capabilities; absence must not be filled with mock entitlements to satisfy legacy type requirements. Persian default is an application preference, not a forged persisted profile.

Cache/query keys include issuer+subject+session generation. On Auth account change/logout, cancel reads, clear account-owned caches and drafts, increment generation, disable saves until new account read succeeds. Every mutation captures expected subject/revision/key; do not replay A's pending operation after signing in B. Late A responses are discarded by generation/subject and revision checks. On409 retain unsaved edits, refetch canonical profile, present explicit conflict resolution; never silently overwrite. On503 preserve edits/session and permit retry; only genuinely unauthenticated401 triggers reauthentication. Server membership remains final even if local UI caches ready state.
