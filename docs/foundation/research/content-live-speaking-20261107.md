## Verified current API facts and limitations

Sources below were fetched on2026-11-07. Shared voice pages currently contain **both** GPT-Live and Realtime sections. This proposal uses the Realtime sections and `/v1/realtime` protocol. Do not mix GPT-Live `session.start`/`session.closed`, duration pricing or reflected-audio promises into Realtime.

- [Realtime overview](https://developers.openai.com/api/docs/guides/realtime) recommends native speech-to-speech for immediate voice conversation, with browser WebRTC or server WebSocket. Its current example uses `gpt-realtime-2.1`. GA uses `session.type='realtime'`, nested `session.audio`, `/v1/realtime/client_secrets` and `/v1/realtime/calls`; the old beta header is removed.
- [WebRTC](https://developers.openai.com/api/docs/guides/voice-webrtc?api=realtime) supports unified initialization: browser SDP goes to the application server, which posts multipart SDP plus server session configuration to `/v1/realtime/calls` with its private API key. Browser receives SDP answer, not the key. Alternatively the server mints an ephemeral client secret and the browser calls OpenAI directly. HTTPS/localhost and microphone permission are needed. Provider SDP/call IDs and ICE addresses are private connection metadata, not logs or public URLs.
- [Create-client-secret OpenAPI](https://developers.openai.com/api/reference/resources/realtime/subresources/client_secrets/methods/create), obtained through the actual OpenAPI tool, explicitly says attached configuration can be overridden by the client connection. Installed `client_secret_create_params.py` says TTL10–7200seconds, default600; expiry blocks new session creation, not an already running session, and **one secret can create multiple sessions before expiry**. A token is not a one-call spending cap, immutable task lock or session revocation mechanism.
- [Server controls](https://developers.openai.com/api/docs/guides/voice-server-controls?api=realtime): unified WebRTC's `Location` returns the call ID; trusted server sideband attaches at `wss://api.openai.com/v1/realtime?call_id=…`. Sideband can observe events/update instructions/execute authorized tools. It does not turn the browser data channel into a server-only command surface or prove speech safe before playback. Do not assume the GPT-Live-only reflected PCM events shown earlier on the shared page exist for Realtime.
- [Hangup OpenAPI](https://developers.openai.com/api/reference/resources/realtime/subresources/calls/methods/hangup), retrieved using endpoint path `/realtime/calls/{call_id}/hangup`, confirms POST ends WebRTC or SIP calls, using the server-captured call ID.200 means termination has begun, not a billed-finality receipt.404 means unavailable/not found, not permission to recreate the call.
- [Realtime conversation lifecycle](https://developers.openai.com/api/docs/guides/realtime-conversations): maximum session duration60minutes. Voice cannot change after the first audio response. Realtime uses `session.created`, `session.updated`, `response.done`; WebRTC/SIP can handle output buffer interruption/truncation, whereas a WebSocket application must stop actual playback and send the heard-duration truncation itself.
- [VAD](https://developers.openai.com/api/docs/guides/realtime-vad) offers server/semantic turn detection. Actual installed `RealtimeAudioInputTurnDetectionParam` permits `create_response=false` and `interrupt_response=false`, preserving VAD events without automatic responses. This is essential for server-reserved responses and Part2 pauses. Leave idle automatic prompting disabled; a learner's planning pause is not authority to start another billed answer.
- [WebSocket](https://developers.openai.com/api/docs/guides/voice-websockets?api=realtime): trusted backend connects to `wss://api.openai.com/v1/realtime?model=…`, keeping API key server-side; audio chunks/events are application-owned. OpenAI normally recommends WebRTC for browser media robustness. A relay adds playback, buffering, interruption and backpressure responsibilities; it needs direct comparative latency/network testing.

[Current model page](https://developers.openai.com/api/docs/models/gpt-realtime-2.1) lists `gpt-realtime-2.1`, same current snapshot identifier,128k context,32,000 maximum output, text/audio/image inputs and text/audio outputs. It is reasoning-capable; higher effort can add latency and output usage. The current generic Realtime session reference/installed SDK accepts integer `max_output_tokens`1–4096 or infinity. This mismatch is a reason to test explicit bounded session configuration, not assume32k output is needed or send infinity. The candidate first experiment binds the exact reviewed model string and a small explicit output cap; no availability/access claim is made. The installed type permits arbitrary model strings, but older generated literals do not prove current-model compatibility or newer reasoning fields.

[Current pricing](https://developers.openai.com/api/docs/pricing), USD per million tokens: `gpt-realtime-2.1` audio input32/output64/cached input0.40; text input4/output24/cached input0.40. `gpt-realtime-2.1-mini` audio10/20/cached0.30; text0.60/2.40/cached0.06. A lower price is not evidence of adequate interviewer quality; compare with teacher-rated identical synthetic traces before choosing it. `gpt-audio-1.5` recorded assessment audio input32/output64 and text input2.50/output10. These are provider prices, not Mitooni prices or authorized budgets. Context is billed repeatedly across responses; do not multiply a single utterance's duration by a rate and call it the full conversation cost. Optional input transcription is an additional billable path. Re-fetch prices/model constraints before any approved run.

[Cost guidance](https://developers.openai.com/api/docs/guides/voice-latency-cost?api=realtime) says Realtime response creation incurs input/output token cost, while connection/network alone is currently not billed. Audio input is roughly10tokens/second and generated audio20tokens/second, with other tokens/overhead; these are planning estimates, not admission proofs. Usage comes from `response.done`, including modality/cache details. Truncation can bound post-instruction context. Cache discounts are best effort and must not fund admission reservations.

Recorded assessment remains a different endpoint: [GPT-Audio-1.5](https://developers.openai.com/api/docs/models/gpt-audio-1.5) and [audio Chat Completions](https://developers.openai.com/api/docs/guides/audio-chat-completions) confirm actual audio input with `input_audio` and WAV/MP3 support. Its features do not establish Structured Outputs support. Keep existing textual JSON instructions plus strict four-criterion/evidence validation, `store=False`, no SDK retries and actual byte-hash binding. Live conversation is not an unverified real-time grade.

## Transport challenge and recommendation

**Proposed first controlled integration: browser → authenticated Mitooni WebSocket media relay → server-owned OpenAI Realtime WebSocket.** Use a short-lived one-use **Mitooni** connection ticket, never a provider API key or direct provider client secret. This still provides actual native live speech interaction. The extra relay is justified by the requested server authority, response budget cap, auditable original samples and task/phase conditions. Latency/reliability must be measured; if unacceptable, revisit the tradeoff rather than silently weakening controls.

Direct WebRTC has the best documented browser media mechanics. Unified server SDP plus sideband is preferable to issuing general ephemeral provider secrets: it captures one call ID and avoids giving the browser a multi-session credential. It is a credible later **formative-practice** alternative when residual client mutability is accepted. However, browser `session.update`/`response.create` can alter instructions/output caps and start responses; sideband correction/hangup races that action. Do not call its application budget reservation a strict provider spending firewall or claim independent assessment conditions. A trusted WebRTC media bridge terminating the browser connection could enforce commands, but adds a larger media stack than the narrow relay. No new bridge/service is proposed now.

A short-lived direct OpenAI secret is therefore not the recommendation for this controlled beta. If a later design selects it, document multi-session reuse, configuration override and ongoing-session expiry limits explicitly and obtain the coordinator's security/cost decision. No browser prompt or hidden React button fixes them.

## Spending and assessment boundaries

An app timer or number-of-sessions quota is not a monetary cap. Proposed relay admission uses administrator-configured integer micro-USD ceilings, exact price/model version, maximum context and billable output ceilings, maximum response count and a distinct reserved evaluation amount. No amount is invented here. Before each server response.create, atomically reserve a conservative worst-case response ceiling and persist a dispatch marker; if insufficient, do not send. Use the highest accepted input/output modality price, ignore caching savings and include any separately enabled transcription/tool cost. Prefer disabled optional tools/ASR for the first slice. Prices/output accounting or explicit caps not established for a chosen model mean fail closed; do not fund reservations from an unmeasured duration estimate.

Upper-bound formula is `maxAcceptedInputTokens × maxInputRate + maxBillableOutputTokens × maxOutputRate`, converted with ceiling arithmetic and protected overhead. The model's documented full context/output bounds provide a very conservative starting ceiling; a smaller configured response cap can replace the model maximum only after exact SDK/provider accounting establishes that all billed output classes obey it. This may be deliberately restrictive until authorized measurement. Use a bounded context configuration and response count to make actual practice useful without claiming a cheaper price is guaranteed.

On response.done, validate modality usage and settle against reservation. Missing, malformed or larger-than-reserved usage stops the session and records unknown/exceptional accounting, never silently refunds/retries. Hosted account controls and billing alerts remain additional defenses; this application cannot promise provider invoice reconciliation or zero external billing error. Reserve interrupted/unknown responses at their full admitted ceiling. Evaluation is separately idempotent and separately reserved; finishing live speech does not authorize an unbounded second model call.

Finalize an immutable learner WAV segment from the exact server-captured input samples, with original sample offsets and related examiner/event manifest. Feed it through existing `admit_wav` and `SpeakingInput`/`SpeakingRunner`/fenced job validation. Add a **server-only** live-session/assistance provenance binding to submission; a browser must not pretend a live coached answer is independent. Existing candidate schema remains four qualitative criteria with recording hash/time evidence or insufficient evidence, model-estimated timestamps, no band/overall/CEFR field. Transcript can aid lexical/grammar work but cannot substitute for pronunciation/temporal fluency audio. Do not mix examiner audio into the learner-only evidence track or remove pauses to improve fluency. Missing/damaged/chopped samples and short fragments require abstention/limits.

Raw sources remain in the private authoring layer; live provider receives only approved serving task/phase context needed now. Speech, task text, transcripts and source-derived excerpts are untrusted content: delimiter treatment and role instructions are defenses, not perfect injection filters. The relay's allowlist, no external tools, server phase authority, private-answer exclusion, owner checks and immutable provenance carry the enforceable boundary. Teacher checks must still detect conversational drift, hints and inappropriate speech already heard.
