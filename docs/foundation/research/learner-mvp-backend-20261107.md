## Alternatives and recommendation

A. Expose the review beta to candidates. Small apparent effort but wrong roles, reveals, state and claims; rejected.

B. Grow the single study JSON and flat pack list. Fast for another engineering slice, but lifetime size/turn caps, generic text responses and fixed-next-step policy preclude the requested full learning product; rejected as MVP architecture.

C. Preserve account/BFF/RLS and worker semantics, add normalized candidate records, adapt admitted licensed content into one versioned candidate catalogue, and create deterministic evidence-based plans with generated teaching/feedback. Recommended smallest complete backend. One FastAPI app, PostgreSQL, current SDK adapters and bounded job queue; no new orchestration service, universal exam engine, vector infrastructure or payment platform required.

The AI remains central: it explains source teaching, asks questions, diagnoses attributable learner work, provides repair actions, adapts explanations/examples and proposes an appropriate next activity from permitted alternatives. Server policy validates choices; it does not replace teaching with fixed snippets. It may not invent new assessable items/answer keys or publish content on the learner path. Future generation can supply new admitted catalogue editions without changing attempts or client contracts.

## Exact proposed candidate contract

This is a proposed API v2 namespace to preserve accepted `/api/study` foundation clients until migrated. Requests use strict extra-forbid schemas. Mutation identity and retry convention remains `Authorization`, `X-Expected-User-Id`, `Idempotency-Key` UUID, expected revision and canonical request hash. Same key/body returns same committed result; same key/different body conflicts. Candidate access requires an explicit admin-managed learner grant distinct from all three existing review-only accounts; onboarding, user metadata and reviewer permission never self-grant study or tutor rights. All reads, replay outcomes and mutations recheck current active candidate membership/entitlement; UI never supplies role or approval.

Common references: `ContentRef {catalogId,catalogVersion,catalogHash,unitId,unitVersion,unitHash,assessmentVersion,policyVersion,familyRegistryVersion}`; `EvidenceRef {id,kind,attemptId,contentRef,conditions,createdAt}`; `WorkRef {kind:draft|attempt,id,revision}`. Common response capabilities are server-computed, not implied by visible buttons. All timestamps are UTC ISO strings; server owns start/deadline/receipt time. Client receives `serverNow` for timer display only.

1. `GET /api/learner/bootstrap` -> account summary, candidatePreferences, activeBaselineRef, activePlanRef, resumableSessionRef, capabilities and missing setup fields. No transcript/audio bodies here.
2. `PATCH /api/learner/preferences` `{expectedRevision,examTrack:academic|general_training,weeklyHours,testDate?,targets,selfReportedLevel?}` -> versioned preferences. Keep account locale/theme/name; alias existing currentLevel to selfReportedLevel and migrate explicitly. Preference changes never rewrite old attempts. Track change creates a new compatible plan; shared skill evidence may be reused only by explicit policy, while track-specific Reading/Writing is retained as history.
3. `POST /api/learner/baselines` `{expectedPreferencesRevision}` -> `Session {kind:baseline,status:ready,contentRefs,sectionStates,revision,conditions}`. Policy selects an admissible four-skill baseline for track and declared starting branch; no score inferred from selection. `POST .../sessions/{id}/start` starts the first section, fixes deadlines and records exposure. Baseline may be resumed with all four skill states explicit, including missing/insufficient evidence; incomplete is not a complete overall result.
4. `GET /api/learner/plans/current`; `POST /api/learner/plans` `{expectedPreferencesRevision,expectedEvidenceRevision}` -> deterministic versioned candidate plan. `Plan {id,version,status:active|superseded|needs_attention,preferencesRevision,evidenceRevision,policyVersion,contentCatalogRef,steps:[{id,kind:lesson|practice|repair|transfer|mock,skill,objectiveIds,contentRefs,estimatedMinutes,prerequisiteStepIds,state:available|locked|in_progress|completed|unavailable,reasonEvidenceIds}],weeklyCapacityMinutes}`. Deterministic policy selects real content, obeys prerequisites, balances four skills, prioritizes evidenced gaps and never schedules more than available time. Missing date/capacity yields explicit unscheduled state, not fabricated deadlines. Completion means required work submitted/reviewed according to policy, not mastery.
5. `POST /api/learner/workspaces/resolve` `{planId,planVersion,stepId,conditionPreset:supported|independent}` -> pinned Workspace. `Workspace {id,revision,contentRef,attempt,draft,task,capabilities,latestJobRef}`. Existing matching open step resumes its exact edition and conditions. `PATCH /.../workspaces/{id}/draft` `{expectedDraftRevision,responses:[{itemId,response:<typed union>}]}` -> acknowledged revision; atomic submission requires matching workspace/draft/conditions revisions.
6. `POST /api/learner/attempts/{id}/submit` `{expectedWorkspaceRevision,expectedDraftRevision,expectedConditionsRevision}` -> immutable attempt and deterministic result/feedback status. `Attempt {id,parentAttemptId?,status:open|submitted|expired,contentRef,conditions:{original,current,assistance,exposureEligibility},startedAt,deadlineAt?,submittedAt?,responseHash}`. No browser-written score, mastery, elapsed total or completion flag. Deadline expiration freezes last acknowledged draft; a late never-acknowledged response is refused clearly.
7. `POST /api/learner/workspaces/{id}/assistance` explicit consent body and condition revision. Independent -> supported is one-way for that attempt. `POST /.../workspaces/{id}/turns` retains intent/workRef/revision and returns durable Job; `GET /.../jobs/{id}?after=N` and cancel use bounded public events. Tutor unavailable returns provider-unavailable capability/status while work stays saved; no invented feedback or silent synthetic runner. A feedback job references submitted immutable work, exact rubric/anchors and target locale.
8. `POST /api/learner/attempts/{id}/revisions` `{expectedWorkspaceRevision}` creates a supported child attempt; never overwrite original. Feedback can propose repair options already admitted by policy. `POST /api/learner/plans/{id}/proposals/{proposalId}/accept` `{expectedPlanVersion,expectedEvidenceRevision}` verifies evidence, allowed alternatives, content availability, time budget and eligibility before atomically creating new plan version. Proposal unavailable after evidence/preferences changes requires recomputation; model prose never mutates journey directly.
9. `POST /api/learner/sessions` `{kind:mock,mockId,mockVersion,expectedPlanVersion?}` -> pinned four-skill session. Section state `locked|ready|running|submitted|expired|review_pending|reviewed`; session state `ready|running|submitted|review_pending|completed|abandoned`. Baseline uses same session engine, different teacher-defined assessment policy. Timing/replay/pauses are explicit policy. No global independent claim if section assistance/exposure disqualifies it. Mock is full length only if all required admitted sections/assets, timing, input and scoring paths are present; otherwise catalogue advertises practice sections instead.
10. `POST /api/learner/attempts/{id}/recordings` binds item ID, contentRef, expected attempt/draft revisions, declared hash and bytes. Hash/size/type/duration measured on server; accepted audio becomes immutable recordingRef. `GET /.../recordings/{id}/audio` owner-only. Each Speaking turn fits bounded WAV limits; interview is ordered multiple turns under one session, not a 15-minute upload to the 180-second rehearsal endpoint. Client capture needs tested bounded resampling/encoding or a separately reviewed decoder; existing WAV validation alone does not establish mobile recording compatibility. `POST /.../attempts/{id}/feedback` reserves actual waveform job, not transcript-only substitution.
11. `GET /api/learner/progress` -> four skill entries, coverage by objective/family, recent raw accuracy with item denominator, supported/independent/previously exposed separation, submitted/revised activity and attributable feedback/actions. Include missing evidence plainly. No predicted overall, no averaging short-drill accuracy into bands, no merging mock raw accuracy with qualitative Writing/Speaking into a false band. Validated teacher band assessments, if later supported, have separate provenance and instrument scope.

Stable unavailable/error codes: `access_required`, `revision_conflict`, `content_changed`, `content_gap`, `content_withdrawn`, `condition_switch_required`, `submission_required`, `assessment_not_complete`, `deadline_passed`, `provider_unavailable`, `provider_rate_limited`, `budget_exhausted`, `dispatch_unknown`, `invalid_audio`, `storage_limit`. Errors return safe recovery action and request/operation identifier, not provider exception, prompts or source details. Unknown acknowledgement recovery first GETs canonical state/replays same operation, never starts a new model call automatically.

## Minimum durable storage proposal

Keep existing account tables and immutable publication registry; expand publication with admitted typed content projections/private assessment reference. Keep review tables isolated. Add owner-scoped normalized candidate tables rather than hiding lifetime work in `study_states`:

- `learner_journeys`: one active preferences/plan/evidence revision pointer per product/issuer/subject; versioned plan snapshots in `learner_plan_versions` keyed journey+version, with frozen inputs/policy and supersession reason.
- `learner_sessions`: baseline/mock kind, track, pinned instrument versions, conditions, ordered section states/deadlines. `learner_workspaces`: plan step/session section, pinned content, draft JSON typed responses, bounded revision, current attempt and active job pointer.
- `learner_attempts`: immutable response snapshot/hash, times, eligibility/assistance, parent linkage and deterministic check. Enforce immutable response body/hash in SQL: INSERT/SELECT-only submitted-response rows with separate lifecycle rows, or a database trigger rejecting any submitted response/hash rewrite. Repository conventions alone are insufficient. Record recordings outside response JSON.
- `learner_evidence`: append-only bounded facts with kind `raw_check|submission|assistance|exposure|ai_observation|human_assessment|revision`; exact attempt/content/actor/work refs and evidence-revision watermark. AI observation is fallible formative evidence, not numeric mastery. Deduplicate by originating immutable event; progress recomputes from facts without repeated-count inflation.
- `learner_jobs`: generic text/audio feedback and planner-proposal durable status/fence/lease/dispatch binding, bounded terminal candidate/output, usage and error code. Reuse queue/worker behavior from current tutor, not source global config. Terminal messages are paginated job artifacts; cap per payload, not 32 lifetime turns.
- `learner_recordings`: immutable owner/item/attempt hash, measured metadata and private bytea for bounded MVP plus explicit per-owner/global storage quotas/retention; no extra storage service needed initially. Separate bytes from ordinary workspace queries. If storage scale requires object storage later, introduce its private object adapter deliberately.
- `learner_operations`: idempotency outcomes bound owner+route+target+operation+request hash with retention policy adequate for offline retry. `provider_usage_reservations`: server-only global project/budget-period + owner limits, price version, model, worst-case reservation, actual modality usage and dispatch-unknown settlement. Cap/currency/pricing policy is admin-owned and read-only to API; reservations use atomic project+owner comparisons across text/audio in the same ledger. The API/user/model cannot alter cap or rate revision. No browser grants and no user-subject diagnostic details in broad logs.

All owner tables use composite product/issuer/subject, RLS, default deny to browser, non-BYPASSRLS API role, matching transaction-local issuer/subject and membership lock/recheck. Foreign keys include owner to prevent cross-owner linkage. Separate publisher role controls publication; worker has only bounded app transitions, not publish/membership modification. Worker dispatch metadata may be visible service-wide to claim jobs but never makes payloads bypass owner scope. Every operation rechecks publication and active membership before dispatch/release; old queued work cannot execute after revocation.

Plan generation/checks are pure functions over versioned preferences, admitted content index and evidence snapshot, then atomically committed with expected revisions. This permits reproducible tests and receiving migrations without another AI planning framework. LLM proposes only allowed IDs and gives learner-facing rationale/teaching; changing the decision policy requires versioned code/teacher validation.
