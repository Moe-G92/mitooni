## Build boundary

Build only from a fresh context generated by `prepare_context.py` from an explicit immutable teacher edition/hash. The assembler calls the actual content pipeline's `load_package` and `require_review_media`, requires the hash-named edition, copies only `package_paths` into `private-review/`, validates curated JSON/PNG/MP3/WAV/spec paths and bytes, then reloads the destination graph. It rejects missing/tampered/unlisted/symlink files. The remaining context consists only of named frontend/build/lock/deploy files, frontend code and backend Python source; `.env`, source originals, corpus SQLite/page extracts, batch outputs, upstream rasters, proposal Word files and review siblings are never copied or read. No broad `review/**` copy is used.

The assembler creates an exact-file Docker ignore list. Negated parent directories and recursive private-file exceptions are forbidden: they can admit unwanted descendants. `context-manifest.json` records admitted paths/SHA-256 and package/asset/assessment-hold counts locally; it is not served or copied into the image. Generated contexts are never overwritten. The repository-root Docker ignore deliberately does not admit `private-review`; building directly from repository root fails instead of silently selecting stale author inputs.

## Runtime contract

Bind variables through the authorized host's secret/configuration interface; do not paste values into reports or command history. Application code reads these variables directly and never reads `.env`:

- `PORT`: Railway listener port, numeric 1024–65535; binds `0.0.0.0`.
- `MITOONI_BETA_HOST`: exact lowercase HTTPS service hostname, without scheme/path/port. Only this Host and `healthcheck.railway.app` are accepted. No wildcard host, untrusted proxy headers or custom-domain DNS change is included.
- `MITOONI_AUTH_URL`: exact approved Supabase HTTPS origin, matching the frontend build issuer.
- `MITOONI_AUTH_PROJECT`: approved issuer project ref, checked against the origin.
- `MITOONI_AUTH_SERVICE_KEY`: legacy name; bind the dedicated project's public publishable key, not an elevated service/secret key. The verified-identity adapter supplies the explicit user JWT to `get_user(token)`. Backend owner verified the installed SDK/header behavior with deny-egress transport fixtures; actual hosted verification remains required.
- `MITOONI_DB_HOST`, `MITOONI_DB_HOSTADDR`, `MITOONI_DB_NAME`, `MITOONI_DB_PORT`: reviewed database target with exact expected TLS hostname and explicit numeric network address; not interchangeable with an unreviewed pooler.
- `MITOONI_DB_PASSWORD`: private password for dedicated `mitooni_api` role. Schema is fixed to `mitooni_app`; non-superuser/non-BYPASSRLS role, verified TLS and schema identity are enforced.
- `MITOONI_REVIEW_PACKAGE_HASH`: exact reviewed canonical package SHA-256, matching the private immutable content copied into this image and the trusted DB reviewer assignments.

Optional Speaking evaluation requires all three variables together: `MITOONI_SPEAKING_MODEL` (explicit supported audio model), `MITOONI_SPEAKING_API_KEY` (private operator-bound key), and `MITOONI_SPEAKING_CALL_BUDGET` (integer 1–8, a per-owner/package model-call ceiling, not a price/spend cap). Partial, blank or invalid binding prevents startup. With none present, provider is `None`, the API reports `available:false` and submission rejects with 503 without queueing work. With all present, the current receiving factory composes the actual SDK Speaking runner and worker. These artifacts do not establish provider account/model access, actual billing, educational quality or calibrated bands; no private key/model/budget was supplied or paid call run. The general learner tutor remains disabled.

Existing inherited environment discovery for libpq services is rejected by receiving target code. The entrypoint does not print environment/configuration values or raw startup exceptions. Access logs and application exception detail logging are suppressed; health failures report sanitized status only. This trades detailed hosted diagnostics for confidentiality; use synthetic reproductions and explicit operational checks rather than enabling raw private payload logs.

An authorized administrator must first review/apply `../receiving-schema.sql`, `../content-review-schema.sql`, then `../speaking-review-schema.sql` to the approved dedicated receiving target, including prescribed roles/grants/RLS and the expanded Speaking permission shape. Separately create the intended identity and exact package assignment; Speaking evaluation needs both `review:use` and `review:speaking-evaluate`. These are **not startup migrations**. Do not apply them to SQETutor solely because that project exists. Confirm backup/retention/export/deletion handling and account recovery before activation. No credential, assignment or identity creation is performed by this directory.

For the selected dedicated Supabase target, direct database connectivity is IPv6 unless a separately approved connection option is explicitly verified. Enable outbound IPv6 **on the newly approved Mitooni Railway service** before testing its exact TLS database host/numeric address. Railway documents this as available but disabled by default; enabling it is a staged service change requiring deployment. The receiving target supports numeric IPv6 and keeps the exact `mitooni_api` role. Do not silently switch to an IPv4 shared pooler: its `[ROLE].[PROJECT-REF]` login format is a different contract and is not currently accepted. Verify the actual host connection after approval; local network-disabled image tests do not prove it. Sources checked 7 November: [Railway outbound networking](https://docs.railway.com/networking/outbound-networking), [Supabase connection modes](https://supabase.com/docs/guides/database/connecting-to-postgres).

## Railway manifest and readiness

`railway.json` is a historical review artifact. The current Railway API rejects its Config as Code selector as deprecated; the isolated service uses directly applied Dockerfile path, replica/restart, IPv6, resource-limit and readiness settings. Use the generated context as the build root and the configured nested Dockerfile, or an explicitly authorized exact private image. Do not enable a Git-root auto-deploy: the untracked private immutable edition is intentionally not in Git and direct repository builds lack the generated payload. No upload or image push is performed by the packaging helpers; service configuration changes must remain scoped to the dedicated Mitooni service. No start-command override: image CMD runs the dedicated entrypoint. One replica, limited failure retries and `/ready` healthcheck are specified. This is not a spend cap or continuous monitoring policy. See [Railway config as code](https://docs.railway.com/config-as-code/reference) and [healthchecks](https://docs.railway.com/deployments/healthchecks), checked 6 November 2026.

Startup verifies configured content/hash, matching public build issuer, static index, database TLS/identity, six review/Speaking tables/read grants/RLS metadata and exact assignment column/types. Missing configuration or unavailable storage prevents startup. `/ready` repeats content and database metadata verification and returns only `ready` or `unavailable`. It reads no roster/customer rows and does not infer that an assignment exists. `/health` remains app liveness; Railway must use `/ready`. Auth-provider reachability, permission/policy behavior and actual provider availability need separate checks; readiness is not their proof.

Only exact app routes receive index fallback. Unknown `/api` paths remain JSON 404, private paths are 404, API and HTML responses are no-store. Static files are limited to `/assets/` and `/index.html`; the runtime does not mount the private package. Frontend credentials are session-memory-only in the existing auth adapter: after reload, sign in again and resume durable server state. Test this with the reviewer; do not claim reload persists a login.
