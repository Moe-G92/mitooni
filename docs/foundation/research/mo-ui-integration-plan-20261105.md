## Chosen boundary and alternatives

**Preferred: BarEx auth-only SDK behind an AuthPort, plus typed Bearer BFF transport, adapted to Mo's views.** Reuse session subscription/initial-session handling, auth-only browser scope, expected-user token checks, controlled refresh and bounded error parsing. All application data uses the receiving BFF. The existing receiving backend already enforces verified Bearer identity; no second session protocol is needed for this checkpoint.

Cookie façade alternative: a same-origin server exchanges/manages provider sessions and exposes cookie-authenticated versions of Mo's API. It could retain more mock call signatures, but requires a new session store/cookie renewal/logout bridge, CSRF/origin policy and provider/server auth design. It does not fix profile/membership ambiguity and is more work than adapting the thin client. Reject for this bounded slice; revisit only with a concrete requirement for server-only browser tokens. Do not mix both protocols accidentally or send credential cookies with Bearer requests.

Copying BarEx's whole frontend/AuthContext/api monolith is also rejected: it imports source configuration, creates its SDK client at module import, carries commercial intent/default plans and cannot preserve Mo's visual ownership. Adapt the smallest actual source ranges and record source hashes; provider verification/testing is repeated in Mitooni.

## Concrete account contract agreed with backend specialist

Keep `GET /api/me` unchanged as verified identity for compatibility with S1. Add **`GET /api/account`** as the only new bootstrap request, with a runtime-validated envelope:

```text
identity: { id, email: string|null }
profile: null | {
  name, locale, theme, targets, testDate, currentLevel, weeklyHours,
  showFlag, notifications, onboarded, revision
}
membership: { status: none|inactive|active, roles: [], entitlements: [] }
state: access-required|setup-required|ready   # derived from the above, not client authority
```

Membership and permissions are trusted backend records keyed by product plus verified issuer/subject, never user metadata, email/domain or a caller-supplied user ID. Valid shared-project identity does not automatically create Mitooni membership. `none/inactive` gives no permissions and denies profile writes; return an explicit access-required state without fabricated profile defaults. The local fixture can seed a trusted active learner; this proves the integration, not public signup/enrollment policy. Real acquisition/invitation/payment enrollment remains outside this slice and must be deliberately specified.

`POST /api/profile/onboarding`: authenticated active-member only; validated full learner setup plus `expectedRevision:0`, atomically create/complete version 1. Profile may be null before this operation; frontend builds a separate onboarding draft from explicit user inputs and safe display defaults (`locale:fa`, light display), never a demo person/score/target. Concurrent/duplicate creation must not reset an existing profile. Use a stable operation ID or documented conflict/refetch reconciliation for lost acknowledgments; do not generate new IDs on each transport retry.

`PATCH /api/profile`: narrow editable DTO plus `expectedRevision`. Allow only name/display preferences, self-reported goals/currentLevel, testDate/study hours, review-flag and notification preferences. Reject unknown fields and stale revisions with 409; update atomically. Identity/email, membership, roles, entitlements, plan and approved exam timing/accommodation are absent from this DTO. Identity changes belong to a separate verified auth workflow; Settings may display identity email read-only with the same field presentation. No invented plan/pricing copy or auto-upgrade endpoint.

Read-only server-owned accommodation/schedule compatibility fields must be explicitly returned before legacy exam screens need them; do not synthesize a complete `Profile` by filling missing `plan` or other authority fields. Introduce `Account`/`LearnerProfile`/`ProfilePatch` schemas and narrow Mo view selectors. Update directly affected consumers rather than a broad cast. Where a non-authoritative visual field is absent, use existing honest unavailable/empty treatment.

New endpoint error envelope: prefer `{detail:{code,message,fields?}}` with stable codes for session-required, membership-required, stale-revision, validation and unavailable; preserve legacy `/me` string detail. Frontend parser accepts string/object/422-detail-array forms but maps them to localized Mo messages and field errors, not raw provider exceptions or arbitrary response bodies. A 401 can trigger one refresh; 403 does not sign the learner out; 409 preserves the current draft; 422 shows fields; 503/network show retry/outage without deleting a valid session; invalid schema fails closed. All account/profile responses are private/no-store.

## Session and cache algorithm

Maintain a session snapshot `{status, subject, epoch}` where status distinguishes initializing, signed-out, authenticated, signing-out, unavailable and password-recovery. Auth-state callback is synchronous: update snapshot and schedule work outside it. Handle initial session, sign-in/account change, sign-out, token refresh, user update and recovery explicitly; unsubscribe on teardown. Token refresh for the same subject does not itself grant new product access.

Every request captures expected subject **and epoch** before token lookup, checks again after refresh/before send, after response and before any cache/draft commit. Capture once per user operation. A caller switching to B must never refresh/retry A's mutation with B's token. Cancel old requests with AbortController, but also ignore their late success/error callbacks: abort alone cannot undo a server commit. Server uses the verified subject, never a client identity field; use stable mutation IDs and revision checks. Replay after 401 only if authentication failed before mutation commit and the same operation/epoch remains valid.

On account change or local sign-out: increment epoch immediately, cancel owned queries, discard the old private QueryClient or remove all private queries/mutations, remount account-owned forms/routes keyed by epoch, clear namespaced private drafts and prevent old callbacks from writing. Account-scoped keys include subject and epoch; shared public content keys are allowed only for explicitly public immutable content. Disable account queries until session initialization resolves; public pages must not call `/account` as an anonymous probe. Replace the current `useMe` pattern with an enabled account selector under session provider so `PublicLayout` and `LanguageSwitch` do not trigger unauthenticated private fetches.

Sign-out must hide private UI/cache immediately, even if revocation is offline or fails. Use explicit current-session/local scope and report a recoverable revocation limitation; do not copy source default-global behavior blindly. Sign-out is not a claim that already-issued access JWTs are immediately revoked. For the same reason every sensitive backend operation rechecks active membership/assignment. Preserve non-private language preference. An explicit “all devices” action is future scope, not the default account menu action.

Bootstrap/guard order: configuration → auth initialization → signed-out or recovery → account load → membership gate → nullable-profile onboarding → ready route. A ready account is not evidence that learning endpoints exist. For this slice, only onboarding/settings/account are backend-enabled; existing Mo learning routes remain explicit unavailable capability states rather than MSW/sample results. Do not expose staff/coaching roles or new public offers from a default profile.

Sanitize `next` to a relative allowlisted Mitooni destination (initially account/settings plus agreed ready landing). Reject protocol/`//`, backslashes, control characters, malformed encodings, auth/callback loops and unknown paths. Apply the same redirect-origin validation to recovery/confirmation callbacks. No URL token is logged or used as a membership grant.
